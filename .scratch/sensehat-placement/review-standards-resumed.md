## Documented violations

1. **P2 — Receipt evidence can falsely pass.** `verify.py:38–70` checks outer request identity and hash links but never validates stage `request_id`/`run_id`, `input_bytes`/`output_bytes`, or source `payload_bytes`. An in-memory Python `-B` reproduction with every stage byte count set to −999 and receipt identities set to WRONG returned `problems=[]`. This violates implementation-task.md “all-stage receipts … input/output sha256+bytes” and verifier “actual receipts … input/output hash chain,” plus AGENTS.md’s requirement to distinguish Task bytes from telemetry. Validate identities against the run/request and byte counts against frozen payload/reference evidence and adjacent receipts; add a rejection case.

2. **P2 — Frozen code provenance is recorded but not verified.** `forecast.py:208–222` writes `code_sha256` but checks only data-file hashes; `run.py:220–255` accepts the prepared bundle and copies/hashes the current implementation. `verify.py:152–160,252–264` compares shipped runtime text with its newly copied counterpart, without reconciling either with frozen code hashes. A post-prepare runtime edit can therefore execute against the old preparation while verification lacks a code-provenance failure. Standard: implementation-task.md frozen-hash verification and AGENTS.md preservation of frozen sources/provenance. Reconcile preparation, execution copies and shipped runtime hashes, or require an explicitly new preparation.

3. **P2 — Cleanup lacks phase boundaries.** `run.py:351–352,382–424` invokes teardown outside `rec.phase`; only individual command logs are retained. `verify.py:223–227` accepts whichever phases happen to exist. Standard: AGENTS.md explicitly requires new collection phase start/end events; the task also requires deployment/warmup/collection costs separately. Record teardown start/end/status/duration so interrupted cleanup and its cost have explicit phase evidence.
