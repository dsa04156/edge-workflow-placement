# 기존 스케줄링과 프로파일 기반 배치의 우선 비교

2026-10-21. 사용자 요청에 따라 선택적 프로파일링보다 기본 배치 비교를 우선한다. 아래는 사전 설계와 오프라인 결정 대조 기록이다. 후속 축소 실측은 [소규모 실측 결과](scheduling-baseline-smoke-20261021.md)에 기록했다. 평가9/9 성공 후 최종 제어 exec EOF로 중단돼 전체 감사는 partial이다.

후속 사용자 지시로 대규모 반복 대신 최소 실험을 구현한다. 아래 2block/40평가 설계는 후속 본 실험 후보로 남기고, 이번 실행은 [축소 구현 계약](../../.scratch/scheduling-baseline-comparison/implementation-task.md)의 1block·10/2Mbps·보정4입력·고유 배치당 평가3입력으로 제한한다. 비교 정책은 kube-default/greedy/heft/greedy-swap/exact/no-network의 6개다. 실측 완료 여부는 후속 결과 문서로 기록한다.

## 먼저 검증할 질문

같은 영상·음성 → 결합 워크플로에서 실제 기본 스케줄러에 비해 연산·전달 프로파일을 이용한 배치가 실제 완료시간을 줄이는가? 개선이 있다면 정보의 추가 효과인가, 같은 정보를 이용하는 배치 알고리즘의 차이인가?

비교 순서는 기본 스케줄러 → 프로파일 기반 단순 배치 → 기존 DAG 휴리스틱 기반 변형 → 단순 보완 → 정확 열거다. 현재 `ours`라는 코드 키는 작은 문제의 정확 열거이며, 새로운 알고리즘으로 명명하지 않는다. 별도의 새 알고리즘 우월성을 전제하지 않는다.

## 비교군과 정보 계약

| 구분 | 실행 방식 | 사용하는 정보 | 해석 |
|---|---|---|---|
| K0 기본 Kubernetes | 실제 default-scheduler, 허용 후보만 동일하게 제한 | 원래 scheduler 정보; 실험용 연산·전달 비용표 주입 없음 | 기존 시스템 기준선 |
| P1 greedy EFT | `placement_policies.sequential(ranked=False)` | 동일 연산·전달 프로파일, 현재까지 선택한 선행 배치, 자원 | 순차 earliest-finish 기준선; compute-only fastest라고 부르지 않음 |
| P2 HEFT-serving | 같은 함수의 `ranked=True` | P1과 같은 표, upward rank | 지속 서비스용 HEFT 기반 변형; 원 HEFT 재현이 아님 |
| P3 greedy 한 번 교환 | `budget_placement.simple_alternatives` | P1과 동일 표·후보·제약 | 단순 보완으로 충분한지 확인 |
| P4 정확 열거 | `prepare.plan(topology_profile)` | P1과 동일 표·후보·제약 | 작은 문제의 모형 최적 기준값; 새 알고리즘 아님 |
| A1 전달 정보 제거 | `prepare.plan(profile_only)` | 같은 표에서 전달 비용만 0으로 두고 선택 | P4 대비 네트워크 정보 효과 |
| A2 노드별 연산 정보 제거 | `prepare.plan(topology_only)` | 작업별 연산시간을 후보 평균으로 통일 | P4 대비 이종 연산 정보 효과 |

고정 서버 배치와 기존 `greedy-swap-move`는 보조 대조로 보존한다. Koordinator·DRL·JellyBean/Atlas/AnchorDL 원 구현 비교는 이번 1차 pilot에 포함됐다고 주장하지 않는다. HEFT 변형 하나로 기존 DAG 기법 전체를 대표한다고 주장하지 않는다. 먼저 작동하는 공통 실행기에서 K0와 위 정책군을 비교한다.

K0 대 P4는 프로파일링과 배치 선택을 합친 **방식 전체의 효과**다. 알고리즘만의 효과는 P1–P4에 같은 동결 profile을 줘서 대조한다. 모든 방식에 동일 모델/품질/실행 후보를 제공하되 K0를 프로파일 기반 정책으로 몰래 바꾸지 않는다.

## 자원 조건의 수정

주 비교에는 실제 잔여 requests 기반 CPU·메모리 snapshot을 사용한다. 최근 `run_budget_placement.py`의 서버 슬롯 2개는 planner에만 적용하는 인위적인 workflow 예산이므로 기본 kube-scheduler와 직접 섞지 않는다. 기본 스케줄러에도 동일 예산을 실제로 강제·검증하는 기능을 만들지 않는 한 슬롯 제한 실험은 별도 정책 진단으로 유지한다.

보정 중 모델 Pod를 제거한 후 snapshot을 동결하며 source/relay/sidecar 등 공통 자원 사용은 잔여량 계산에 반영한다. 작업별 requests/limits, 후보, 이미지, 모델, precision, batch, thread 수는 같다. 새로운 block에서 자원이 달라지면 새 보정/snapshot으로 구분한다. 전체 서버 CPU를 실제로 소진시키는 조작을 슬롯 제한의 대체로 수행하지 않는다.

## 이미 실행한 오프라인 결정 대조

입력은 `wan-20261021t044624/profile-calibration-{10,2}.json`의 실측 비용표다. 서버 슬롯을 줄인 `profile-b0-*`와 구분한다. 각 비용표에서 기존 함수들을 실행해 8정책 × 2조건 = 16개 결정을 [JSON](../../.scratch/scheduling-baseline-comparison/offline-decisions.json)에 저장했다. 파일·구현 hash와 실행 가능성 확인을 포함한다. 다음 값은 **예측 proxy이며 새 E2E 실측이 아니다**.

배치 표기는 영상/음성/결합, C는 서버, E0/E1은 입력 발생 엣지다.

| 방식 | 10Mbps 배치 / proxy ms | 2Mbps 배치 / proxy ms |
|---|---|---|
| 기본 kube-scheduler | 새 관측 필요 | 새 관측 필요 |
| greedy EFT | C/C/C / 683.616 | E0/C/C / 952.991 |
| HEFT-serving | C/C/C / 683.616 | E0/C/C / 952.991 |
| greedy 한 번 교환 | C/C/C / 683.616 | E0/C/C / 952.991 |
| 정확 열거 | C/C/C / 683.616 | E0/C/C / 952.991 |
| 전달 정보 제거 | C/C/C / 683.616 | C/C/C / 1,411.551 |
| 노드별 연산 정보 제거 | E0/E1/E0 / 2,362.503 | E0/E1/E0 / 2,363.318 |

고정 서버는 C/C/C, 교환 후 한 작업 이동은 해당 조건의 정확 열거와 같은 배치를 선택했다. A1/A2의 표 값도 선택 후 원래 full 비용모형으로 평가했다. 정보 제거 목적함수 값을 full proxy와 혼동하지 않는다.

이 대조에서는 추가적인 DAG 탐색의 이득이 관측되지 않았다. 2Mbps의 A1 대비 차이는 전달 정보 활용의 후보 효과다. 실측 검증 전에는 실제 개선율로 쓰지 않는다. 과거 native smoke의 kube-default C/C/C 결정을 이번 WAN 조건의 scheduler 결과로 재사용하지 않는다. 슬롯2 조건의 E0/C/C 실측과 슬롯 제한 없는 C/C/C proxy를 한 성능 표로 합치지 않는다.

## 1차 실측 pilot의 고정안

- DAG: ResNet18 영상 특징, Wav2Vec2 전사, MUTAN 결합. 기존 FP32/CPU/batch1 및 품질 기준 유지. 이미지 E0·음성 E1 파일 재생, 같은 직접 전달 실행기.
- 조건: compressed 입력의 정적 10Mbps/2Mbps, 방향별 추가 지연 20ms. 조건마다 동결된 해당 전달 프로파일 사용. native는 후속 대조로 추가할 수 있으나 이번 2조건 결과와 같은 조건으로 합산하지 않는다.
- 단위: 두 개의 별도 보정·선택·평가 block으로 연결 검증을 시작한다. block마다 자원 snapshot과 프로파일을 새로 얻는다. 같은 host/day/cache를 공유하면 독립 환경 반복으로 부르지 않는다. 이는 검정력을 갖춘 본 실험 표본 수가 아니다.
- 입력: 기존 calibration 20쌍과 evaluation 40쌍을 분리한다. 전체 40평가쌍을 각 고유 배치에 동일 순서로 사용하고, 보정 입력으로 warmup 5회를 둔다. 이미 사용한 corpus이므로 새 holdout이라고 부르지 않는다.
- 도착률: 먼저 기존 open-loop 실행기의 0.1 request/s로 고정한다. 이 pilot은 저부하 latency 비교다. 완료율을 기록하지만 최대 처리량 개선으로 주장하지 않는다. 용량 비교는 동일 arrival trace의 별도 부하 단계에서 수행한다.
- 순서: block 내 조건과 고유 배치 평가 순서를 무작위화한다. 실행기가 최종 정책 집합을 확정하면 seed·환경 버전·일정 파일을 수집 전에 동결한다. 현재 일정 미생성 상태로 실측 준비 완료라 표시하지 않는다.
- 동일 배치: 같은 block/조건/상태의 정책이 같은 배치를 고르면 warm E2E 관측을 공유한다. 정책별 계획·선택 비용은 따로 기록한다.

K0는 각 block/조건에서 후보 노드에 pin하지 않은 실제 scheduler 선택을 기록한다. 실제 노드명·Pod UID·scheduler 버전/설정·이벤트·자원 상태를 저장한다. 그 선택 배치를 다른 정책과 같은 실행기로 재배포해 비교할 경우, 이를 **scheduler가 고른 배치의 성능 평가**라고 표시한다. 재배포의 스케줄링 비용을 K0의 원래 선택 비용으로 대체하지 않는다.

## 지표와 비용 경계

1. 각 block·조건의 실제 source `e2e_ms` 평균/중앙값 및 모든 시도 대비 성공·timeout·품질 실패율을 보고한다. p95는 40요청의 탐색적 기술값으로만 남기며 tail 우월성·유의성을 주장하지 않는다.
2. 품질/호환성 검증, 연산·전달 프로파일 획득, 계획, Pod 배포/모델 준비, steady 실행을 분리한다. K0에 불필요한 프로파일링 비용을 부과하지 않는다. 프로파일 방식의 필수 검증에서 이미 얻은 관측은 재사용하고 이중 청구하지 않는다.
3. 실제 운영 방식 전체의 비용은 readiness·프로파일·선택 등 중첩 구간을 포함한 monotonic timeline으로 산출한다. 준비시간과 요청 latency를 임의로 더한 값을 처리량으로 부르지 않는다. 사용 기간/요청 수에 따른 초기 비용 상각은 가정을 명시한 보조 분석으로 남긴다.
4. 정확 열거의 예측 최솟값은 배치 품질 진단에 사용한다. 모형 최적화만으로 실제 E2E 우월성을 주장하지 않는다. 단순 방법과 배치가 같으면 추가 알고리즘 이득 없음으로 보고한다.
5. 기본 스케줄러와 프로파일 방식이 같은 배치를 고르면 steady E2E 차이는 만들지 않는다. 이 경우 준비·계획 비용과 정책 결정 안정성만 달라질 수 있다.

## 실행 전 필요한 연결 작업

기존 `run_placement.py`에는 실제 default-scheduler 선택 경로가 있으나, 1회 baseline 선택·고정된 정책 집합·6평가 요청의 pilot이다. `run_budget_placement.py`는 kube-default가 없는 4정책 슬롯 제한 수집기다. 어느 쪽도 위 명세와 같지 않아 기존 CLI를 그대로 실행하지 않았다.

후속 구현은 별도 수집 진입점과 대응 감사기를 만들고 기존 collector/동결 자료를 보존한다. 최소 수용 기준은 다음과 같다.

- 주 실험에서 모든 정책의 실행 가능 후보·실제 자원 제약 동일, 인위적 슬롯 제한 없음.
- 실제 scheduler가 고른 배치와 고정 서버 배치를 구분; baseline을 Python 점수 근사로 대체하지 않음.
- block별 새 보정, 정책 집합·정보 접근·profile hash·고유 배치 관측 공유 검사.
- E2E와 준비·프로파일·계획 비용 분리, 실패와 timeout의 부분 로그 보존.
- 보호 workload 불변과 run 소유 자원만 정리하는 계약, 실측 전 무작위 일정과 실행 명세 동결.
- 로컬 검증과 독립 코드 검토 후 배포 명세·예상 실행량을 제시. 프로젝트 지침상 클러스터 배포는 승인 후 수행.

구현 역할은 프로젝트의 Orca Codex 설계 → 공식 구독 Claude Opus 구현·테스트 → 독립 Codex 검토를 따른다. 이 문서 작업에는 구현 워커를 실행하지 않았다.

실험 단위·블록화·관측 공유 원칙은 앞서 적용한 `experimental-design` 절차를 유지한다. 절차 출처는 [시나리오 재설계의 출처 기록](../research/scenario-redesign-20261021.md#설계-절차-출처)을 따른다.
