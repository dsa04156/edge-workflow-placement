# 보유 장비 기반 DAG 자동 배치 실험 계획

작성일: 2026-10-20 (Asia/Seoul)
상태: 실행 전 계획. 이 문서 추가로 자동 배치 구현이나 실장비 실험이 완료된 것은 아니다.

## 목적과 범위

센서 위치, DAG 의존성, 작업별 노드 실행시간, 실제 데이터 이동 비용을 이용해 선택한 배치가 실제 종단 지연을 개선하는지 검증한다. 서버 집중도 동일 후보 공간에 포함한다. 혼합 배치를 강제하지 않는다.

이번 범위는 사전 프로파일 기반 정적 배치와 실제 실행 검증이다. 환경 조건이 바뀔 때 새 프로파일로 별도 계획하며, 요청 처리 중 온라인 재배치 효과로 해석하지 않는다. DRL/Koordinator 도입이나 모델 선택 연구로 범위를 확장하지 않는다.

기존 실험은 고정 cloud/edge/mixed 비교였다. 자동 선택 성능의 증거로 재사용하지 않는다.
- [기존 실장비 기록: 고정 커밋](https://github.com/dsa04156/edge-workflow-placement/blob/4dc7550dcc27d34223d98aeee82fc79ed6545662/docs/experiments/topology-profile-load.md)
- 기존 코드 위치: 위 커밋의 experiments/real-topology-live/run_load.py. 현재 main에 해당 파일이 있다고 가정하지 않는다.
- 기존 저부하 관측: 100Mbps에서 서버 집중 772ms, 혼합 865ms; 2Mbps에서 서버 집중 4031.7ms, 혼합 960.4ms. 각 조건 6요청, 단일 배포 기술통계이며 신규 정책 성능/통계적 우월성 근거가 아니다.

## 워크플로우와 공통 실행 계약

이미지 source → ResNet18 특징 추출(V), 음성 source → Wav2Vec2-base-960h 인식(S), V/S 결과 → MUTAN 합류(F) → E0 응답.

- S1/S2/S4/S5 기본 source는 이미지 E0, 음성 E1. S3만 음성 source를 E0/E1로 바꾼다.
- F도 실행 가능한 노드에서 선택한다. F=C 고정은 별도 진단 조건이며 주 실험과 합치지 않는다.
- 첫 단계는 실제 공개 이미지·음성 파일의 엣지 재생이다. 실제 센서 수집이라고 표현하지 않는다.
- 모델 가중치, 정밀도, 입력, task 경계, batch, 요청·메모리 제한, 스레드 수, 실행기와 전송 경로를 정책 간 고정한다.
- 초기 CPU 구성은 기존 1CPU/2GiB·1 Torch thread·batch1을 출발점으로 검증한다. 세 작업 공존이 불가능하면 공통 자원 설정을 평가 전에 수정하고 재프로파일링한다.
- GPU 확장에서는 노드별 사용 가능 GPU/메모리와 실행 자원 요청을 명시한다. GPU 필수 제약을 CPU 후보에 적용하거나, 한 정책만 더 많은 GPU 자원을 받게 하지 않는다.
- 실행 슬롯/작업 큐와 동일 노드 동시 실행 규칙을 문서화한다. 최적화 모델과 실제 실행기가 같은 의미를 가져야 한다.
- 모든 후보 Pod를 상주시킨 채 선택된 Pod만 측정하는 방식은 비선택 모델의 자원 점유를 유발한다. 보정 후에는 선택 배치만 배포하고, 필요한 공통 제어/source 구성은 동일하게 유지한다.
- 준비/모델 로딩/배포 시간과 warm 요청 지연을 별도로 기록한다. warm 성능만으로 배포 포함 성능을 주장하지 않는다.

## 사전 프로파일과 데이터 분리

평가와 겹치지 않는 calibration 입력 manifest를 만들고 모델/데이터/컨테이너/코드 hash를 기록한다. 각 작업×노드에서 워밍업 후 반복 측정하며 평균·p50·p75·p95, 출력 크기, 메모리, 실행 스레드·장치·전력 상태를 저장한다. 입력 크기와 내용에 따른 변동을 보존한다.

실제 서비스 전송 경로와 직렬화 방식으로 노드 쌍별 payload 크기/전송시간을 측정한다. RTT만으로 전송 비용을 대체하지 않는다. CPU/GPU 동시 실행 조합을 별도로 측정해 고립 프로파일의 오차를 확인한다. 간섭 보정 모델을 구현하지 않았다면 정책이 간섭을 고려한다고 쓰지 않는다.

JPEG/FLAC 압축 전달과 decoded 배열 전달을 별도 입력 표현 조건으로 둔다. 같은 표현 조건에서는 source 준비와 decode 포함 범위를 정책마다 동일하게 한다. 인위적 padding으로 네트워크 비용을 키우지 않는다.

프로파일 수집 시간과 데이터량도 기록한다. 평가 중 비용표/하이퍼파라미터를 사후 조정하지 않는다. 런타임이나 자원 설정이 바뀌면 새 프로파일 버전을 만든다.

CPU reference 대비 출력 품질 기준을 평가 전에 고정한다. GPU 수치 오차 허용범위와 ASR 문자열 비교 규칙을 명시하고, 불일치 입력을 결과 확인 후 삭제하지 않는다. 기존 MUTAN vocab/reference의 한계는 유지하며 reference 일치를 VQA 정확도로 표현하지 않는다.

## 시나리오

| ID | 장비/조건 | 변경 변수 | 검증 |
|---|---|---|---|
| S1 | E0/E1/C, 원래 LAN 및 제한 없는 동일 중계 경로 | native vs unlimited relay | 서버 집중이 유리한 조건에서도 올바르게 선택하는가; relay 자체 오버헤드 |
| S2 | E0/E1/C, 이미지 E0·음성 E1 | 공유 WAN 100/10/2Mbps, 방향별 추가 전파 지연 20ms | 전송비와 처리비의 교환관계, 배치 전환 |
| S3 | E0/E1/C, 10Mbps·방향별20ms | source가 E0/E0 또는 E0/E1 | 입력 발생 위치의 영향; 동일 파일·모델 유지 |
| S4 | E0/E1/J0/J1/C, source E0/E1 | 공유 WAN 100/10Mbps·방향별20ms | 가까운 Pi·다른 엣지 GPU·원격 서버의 성능/전송비 교환관계 |
| S5 | S4 구성, 10Mbps·방향별20ms | 낮음/중간/높음 요청률 | 대기·공존 간섭에서 프로파일 예측과 선택이 유지되는가 |

S1~S4는 예비실험에서 미완료 요청이 누적되지 않는 공통 낮은 요청률을 정한다. S5의 세 도착률도 calibration 전용 pilot으로 정하고 평가 전 고정한다. 기존 0.1/0.5/1 rps는 후보값일 뿐 Jetson의 동일 부하 수준을 의미하지 않는다. 각 정책마다 다른 요청률을 주지 않는다.

S2에서는 압축/decoded 입력의 전체 대역폭 sweep을 별도 보고한다. S1/S3/S4/S5의 주 표현은 압축 입력으로 고정하고, 추가 표현 비교를 수행하면 별도 표로 남긴다. 같은 평가 집합을 요청률/배치 비교에 공통으로 사용한다.

네트워크 값은 대표 현장값으로 단정하지 않는 통제 조건이다. J0/J1은 우선 같은 엣지 LAN 영역에 두며, 엣지↔C 경계에 공유 WAN을 둔다. 엣지 간 링크는 실제 측정값을 사용한다. 모든 policy의 경로가 같아야 한다.

두 source의 동시 전송 합계가 공유 cap을 따르는지 양방향 검증한다. 방향별 추가20ms와 애플리케이션 왕복 증가량을 동일시하지 않는다. 기존처럼 실험 전용 중계 namespace에서 제한하고, 공용 호스트 NIC/CNI/기존 서비스는 변경하지 않는다. 직접 우회 여부와 조건 종료 후 큐 drain을 확인한다.

## 비교군과 선택 기준

| 정책 | 의미 |
|---|---|
| kube-default | 실제 kube-scheduler. 버전, plugin/weight, affinity/spread, request/limit, 노드 상태 기록 |
| server-only | 모든 실행 가능한 작업을 C에 배치; 불가능하면 infeasible로 기록 |
| greedy | 동일 프로파일/망 정보로 현재 작업의 입력 전송+완료시간을 기준으로 순차 결정; 자식 배치 look-ahead 없음 |
| HEFT | 동일 DAG/후보/프로파일로 ranking과 earliest finish 배치. 지속 서비스 실행 의미에 맞춘 변경사항 공개 |
| ours | 전체 DAG의 종단 비용을 이용한 공동 선택; 서버 집중 포함 |
| no-network | ours에서 통신 비용 정보 제거 |
| no-node-profile | ours에서 노드별 처리시간 차이 제거; 공통 평균값 등 정확한 대체 규칙 동결 |

작은 3작업 문제에서 ours의 정확 열거는 선택 기준 검증용이며 새로운 탐색 알고리즘이라고 주장하지 않는다. 예측 목적함수는 우선 고정 p75 프로파일 기반 warm 단일 요청 E2E로 명시한다. 평가 평균/p95와 목적함수가 같다고 주장하지 않는다. S5는 이 정적 가정의 스트레스 평가이며, 부하 인지 정책을 추가하면 별도 버전/실험으로 구분한다.

기본 스케줄러도 동일 실행 가능 후보와 자원 제약을 사용한다. 임의의 affinity로 기본 스케줄러를 불리하게 만들지 않는다. HEFT가 가정한 실행 순서와 실제 상주 컨테이너의 동시 실행이 다르면 재현 차이로 명시한다.

## 반복·평가·전수 배치 대조

- 실행 단위는 동일 조건에서 배포를 새로 적용한 한 번의 run이다. 초기 계획은 5개 반복 block이며 최종 수는 독립 pilot의 변동성과 최소 의미 효과를 기준으로 본 평가 전에 동결한다.
- block 안에서 policy/고유 배치의 순서를 seed로 무작위화한다. 입력·도착 trace는 block 내 공통, block 간에는 사전 지정한 다른 trace를 사용한다.
- 새 Pod가 host/driver cache나 물리 장비를 독립으로 만드는 것은 아니다. 시간 block에 대응한 paired 분석을 하며 장비 모집단으로 일반화하지 않는다.
- 한 배포의 수백 요청을 수백 개 독립 반복으로 세지 않는다. 반복 block별 평균·p95와 paired 차이/신뢰구간을 보고한다.
- 초기 pilot은 run당 워밍업 후 10분을 수집한다. 최종 측정 길이는 가장 낮은 요청률에서도 꼬리 지연을 평가할 요청 수가 확보되도록 평가 전에 공통 고정한다. 10분이 충분하다고 가정하지 않는다.
- phase 종료 시 source/operator/전송 큐를 drain한다. timeout/거절도 계획된 모든 요청의 terminal 기록에 남긴다. deadline·큐/동시도착 상한은 pilot 후 공통 동결한다.
- 동일 snapshot에서 동일 배치를 선택한 policy는 고유 배치 관측을 공유하고 선택시간만 개별 기록한다. 별도로 재실행했을 때 noise로 값이 달라지는 것을 정책 효과로 세지 않는다.
- E0/E1/C에서 각 작업이 세 노드에 모두 가능하면 최대 27개, 실제로는 공통 자원/호환성 제약을 통과한 배치만 평가한다.
- 먼저 S1 unlimited relay와 S2 10Mbps의 압축 입력 조건에서 전수 배치를 대조한다. 평가값으로 사전 정책을 보정하지 않는다.
- 평가 집합에서 관측된 최선은 hindsight 참고치다. 절대 최적이라고 표현하지 않고, 그 배치를 선택한 자료와 별도 확인 trace의 성능도 구분한다.
- S4의 최대125개 전수 측정은 필수가 아니다. 정책 비교와 결정 시간/후보 수를 먼저 보고한다.

## 측정 필드와 판정

필수: run/block/condition/seed, profile/code/model/input hash, planned arrival, source, policy, placement, 실제 Pod UID/node/backend, predicted E2E, decision_ms, deployment/readiness_ms, warm E2E, 작업별 처리·대기, edge별 bytes, 성공/timeout/reject, 자원/온도/클럭.

종단 시간은 E0의 요청 시작부터 최종 응답까지 동일 시계로 측정한다. release 지연과 예정 도착 기준 완료시간을 별도 기록한다. 작업 시간은 로컬 monotonic clock으로 측정하고, 동기화가 검증되지 않은 노드 간 timestamp를 빼서 전송시간으로 쓰지 않는다. 중첩 RPC 시간은 합산하지 않는다.

주 지표는 warm 평균 E2E와 계획 요청 대비 성공률이며 p95, 처리량, 선택 오버헤드는 함께 보고한다. 성공 요청만의 낮은 지연으로 실패가 많은 정책을 우수하다고 판단하지 않는다. 과부하는 유한 관측 stress로 보고하고 정상상태 처리량이라고 주장하지 않는다.

평가 질문:
1. 예측 오차 및 배치 순위가 실제 측정과 얼마나 일치하는가?
2. kube-default/server-only 대비 개선이 있는가?
3. 동일 정보 greedy/HEFT 대비 추가 이득이 있는가?
4. 성능/네트워크 정보 제거 시 어떤 조건에서 악화하는가?
5. 이득이 없거나 악화하는 조건은 무엇이며 가정과 어떻게 연결되는가?

## 실행 인계 순서와 구현 상태

1. E0/E1/C의 현재 Ready/자원/기존 workload와 입력 자산 hash를 확인한다.
2. 위 고정 커밋의 기존 실행기를 읽고 현 main과 차이를 검토한다. 파일을 무조건 덮어쓰거나 과거 명령을 새 자동 선택 실험이라고 실행하지 않는다.
3. 작업×노드 품질/자원 gate와 F 이동을 구현하고 calibration/평가 manifest를 분리한다.
4. 프로파일 → policy plan → 선택 배치 배포 → readiness → 공통 trace 평가 → receipts 수집을 연결한다.
5. kube-default/greedy/HEFT adapter와 제거 실험을 같은 실행기에 연결한다. 같은 계획의 관측 재사용을 검증한다.
6. pilot 후 조건표/반복수/도착률/기간/deadline/분석 규칙을 동결한다.
7. S1/S2 및 작은 전수 배치 대조, 다음 S3를 수행한다.
8. J0/J1의 runtime·품질 gate 통과 후 S4, 마지막 S5를 수행한다.
9. 원시 실패/중단 시도와 동결 manifest를 포함해 결과를 별도 새 경로에 저장한다.

현재 이 변경은 문서만 추가한다. 위 3~8단계의 새 자동 실행 명령은 아직 제공하지 않는다. 기존 run_load.py의 고정 배치 실행을 ours 자동 선택으로 표시하지 않는다.
