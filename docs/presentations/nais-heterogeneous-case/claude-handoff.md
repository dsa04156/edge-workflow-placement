## 3. 8번의 메시지와 연구 목표

### 슬라이드에서 전달할 핵심 메시지

> 개별 Task의 연산시간만 최소화하면 데이터 이동 때문에 전체 응답이 느려질 수 있다. 실제 이기종 환경에서 DAG 실행 위치와 전송 비용을 함께 비교하여, 효율적인 배치 조건과 한계를 확인했다.

### 더 넓은 연구 목표 — 현재 성과와 구분

연구의 지향점은 **품질·네트워크·이기종 실행환경을 고려해 AI DAG의 실행 위치를 선택하고, 품질 조건을 만족하는 유효 처리량을 개선하는 것**입니다.

이번 8번의 대표 증거는 그중 **데이터 이동을 고려한 배치가 유리해지는 조건을 확인한 실제 실험**입니다. 해당 실험이 최종 품질 적격 goodput 개선까지 검증했다고 쓰지 마세요.

### 본인 수행 내용

슬라이드에는 다음 네 항목을 짧게 묶을 수 있습니다.

1. 실제 AI 워크플로와 배치 비교 실험 설계.
2. ARM CPU·Intel NPU 서버의 실행 경로 구성 및 실측.
3. Task 실행시간·중간 데이터 크기·전송 조건에 기반한 정책 비교.
4. 반복 측정·실행 증거 검증·이득과 한계 분석.

## 4. 본문에 사용할 대표 실험 — SqueezeNet 3단계 DAG

70초 한 장에서는 이 실험을 중심으로 설명합니다. 다른 모델·다른 실험의 수치를 섞지 마세요.

### 실행 구조

```text
입력 source: Raspberry Pi의 고정 JPEG 재생

T1 전처리 → T2 SqueezeNet 추론 → T3 후처리

각 Task의 실행 위치 후보:
A = Raspberry Pi / ARM CPU
N = Intel NPU 서버 위치

T1·T3: A와 N 모두 CPU 실행
T2: A에서는 ARM CPU, N에서는 Intel NPU 실행

총 배치 조합 = 2 × 2 × 2 = 8
```

3단계 chain도 DAG입니다. 이 대표 실험에는 병렬 분기·합류가 없습니다. 본문의 아키텍처는 위 3단계와 두 실행 위치를 사용하세요.

### 실험 조건

| 항목 | 확인된 내용 |
|---|---|
| 실행 ID | `20261016t111955534665` |
| 입력 발생 위치 | ARM 엣지 고정, 실제 센서 스트림이 아닌 JPEG 재생 |
| 전달 조건 | native / 50 Mbps 제한 / 20 Mbps 제한 |
| 제약 위치 | 실험 소유 Pod network namespace의 TBF |
| 보정·평가 순서 | 조건별 실측 보정 → 배치 계획 동결 → 별도 무작위 순서 평가 |
| 반복 | 새 Pod 배포 3회, 동일 물리 host·날짜·cache 공유 |
| 측정 | 배포·입력·조건별 고유 선택 배치당 warmup 2회 + 측정 5회 |
| 평균 정의 | 각 배포의 측정 5회 평균을 3개 배포에 균등 평균 |
| 같은 계획을 선택한 정책 | 같은 실행 관측을 공유 |

### 정책 정의

| 정책 표시명 | 실제 비교 방식 |
|---|---|
| Task-fastest | 현재 비용표에서 Task별 연산시간이 가장 작은 위치 선택 |
| Data greedy | 같은 표에서 현재 Task의 연산·데이터 이동 비용을 순차 고려 |
| Current DAG | 같은 표로 전체 8개 배치의 비용을 정확 열거 |
| Native 고정 DAG | native에서 정한 계획을 조건이 바뀌어도 유지 |

Greedy도 노드별 성능과 데이터 이동을 알고 있습니다. 무작위·무정보 비교군으로 묘사하지 마세요. Native 고정 DAG와 Current DAG는 현재 조건 정보를 받는지 여부가 다릅니다.

## 5. 본문에 넣을 숫자

### 주 결과: 큰 입력·20 Mbps

| 방식 | 종단 지연 평균 |
|---|---:|
| Task-fastest | **239.12 ms** |
| Data greedy | **63.05 ms** |
| Current DAG | **63.05 ms** |

원 보고서의 감소율은 **73.63%**입니다. 본문 표현은 다음처럼 조건을 붙이세요.

> 큰 입력·20 Mbps 조건에서, 연산시간만 고려한 배치 대비 전송 비용을 고려한 배치의 평균 종단 지연이 73.63% 감소.

### 왜 빨라졌는가

- 해당 입력 JPEG: **527,940 B**.
- 전처리 출력 tensor: **602,112 B**.
- 추론 출력: **4,000 B**.
- Current DAG와 greedy는 **AAA**, 즉 모든 Task를 ARM에 두는 계획을 선택했습니다.
- AAA는 원격 Task payload가 **0 B**입니다. 제어 통신까지 포함한 전체 네트워크 트래픽이 0이라는 뜻은 아닙니다.
- 따라서 이 결과는 **원격 데이터 이동을 줄인 배치 효과**입니다. NPU가 항상 최선이라는 가정을 실측으로 점검한 사례입니다.

### 작은 반례 또는 보조 문구

| 조건 | Task-fastest | Current DAG | 해석 |
|---|---:|---:|---|
| 작은 입력·native | 26.89 ms | 27.04 ms | 이 조건에서는 DAG가 더 빠르지 않음 |

본문의 핵심은 조건별 효율 차이입니다. 대표 개선 수치를 모든 입력·네트워크에 일반화하지 마세요.

### 검증 규모 — 필요하면 작은 보조 문구

- 전체 실행 **1,340회** = 보정 864 + 평가 476.
- 평가 476회 = warmup 136 + 측정 340.
- 단계별 실행 receipt **4,020개**.
- 유효 완료 1,340회, protocol 실패 0.
- CPU reference Top-5 순서 불일치 0. 정답 라벨 정확도를 의미하지 않음.

‘독립 평가 표본 1,340개’라고 쓰지 마세요. 반복·보정·warmup과 공유 관측을 포함한 실행 수입니다.

## 6. 한 장 구성안

### 제목 — 사용자 확정 제목 유지

**이기종 워크플로 배치 최적화 연구**

### 제목 아래 한 줄

**Task별 연산 성능과 데이터 이동 비용을 함께 고려한 실행 위치 비교**

### 왼쪽: 문제와 실행 구조

- 질문: ‘각 Task를 가장 빠른 장치에 보내면 전체 응답도 가장 빠를까?’
- 3단계 DAG와 ARM / Intel NPU 서버의 두 실행 위치.
- 후보 8개, 실행시간·payload·전송 조건 실측.
- 단순한 흐름으로 표시하고 5단계 VQA 구조를 대신 사용하지 않음.

### 오른쪽: 대표 비교 결과

- 조건: 큰 입력, 20 Mbps.
- Task-fastest 239.12 ms / Data greedy 63.05 ms / Current DAG 63.05 ms.
- 강조: **평균 종단 지연 73.63% 감소**.
- 근거 문구: ‘전송 비용을 반영해 AAA 선택 → 원격 Task 데이터 이동 제거’.
- 작은 반례: ‘작은 입력·native에서는 26.89 vs 27.04 ms로 이득 없음’.

### 하단: 직무 연결

> 장치의 단독 벤치마크를 실제 워크플로의 실행 위치 판단으로 연결하여, 이기종 자원 효율화 조건을 검증.

### 최소 각주

> 조건별 사전 보정 후 평가 · 동일 배치는 관측 공유 · greedy와 DAG 동일 결과 · 새 알고리즘 우월성·품질 적격 goodput 검증 아님

상세 한계는 발표자 메모로 옮기고, 작은 글씨로 모든 설명을 본문에 밀어 넣지 마세요. 그래프·사진은 사용자가 직접 제작할 수 있도록 수치·범례·구성 의도를 명확히 제공하세요.

## 9. 발표에서 지킬 표현 경계

- 구현한 배치 정책은 기존 worker 사이의 Task 실행 위치를 선택합니다. kube-scheduler 자체 개발, Pod live migration, 모델 상태 이전이라고 쓰지 마세요.
- 8개 배치 정확 열거는 작은 DAG의 비교 방법입니다. 새 알고리즘, 선행 논문 구현 재현, DRL 성과로 쓰지 마세요.
- 대표 조건에서 greedy와 DAG는 같은 계획·같은 관측입니다. 두 독립 실험이나 DAG만의 독자적 우월성으로 쓰지 마세요.
- 조건별 사전 프로파일을 제공했습니다. 온라인 네트워크 변화 감지·관측·재배치 전체 비용을 해결했다고 쓰지 마세요.
- 20/50 Mbps는 실험 Pod의 전송 제약입니다. 실제 WAN·물리 NIC 대역폭 전체를 바꾼 것으로 쓰지 마세요.
- CPU reference 출력 일치와 정답 라벨 정확도를 구분하세요.
- 종단 평균 지연 결과를 처리량·p95·SLO 개선으로 바꾸지 마세요.
- 이 저장소만으로 Kueue/HAMi/DCGM, Kubeflow/MLflow, Slurm, 완성된 CI/CD·자동 롤백의 실적을 추가하지 마세요. 해당 발표 장의 별도 근거를 사용하세요.
