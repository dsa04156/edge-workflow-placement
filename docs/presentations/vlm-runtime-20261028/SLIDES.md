# 발표용 문구

## 슬라이드 1 — 최신 VLM의 GPU·NPU 실장치 실행 확인

그림: `vlm-latency.png` 또는 SVG.

- Qwen3-VL-2B 계열, 고정 입력 4개 × 10회/장치. 준비 검증 4회/장치는 별도 보존.
- Jetson Orin BF16: 40/40 성공, 요청 지연 p50 **26.21초**, p95 **27.46초**.
- Mobilint ARIES W4V8: 40/40 성공, p50 **0.367초**, p95 **0.472초**.
- GPU 전체 파라미터·버퍼·출력은 CUDA, NPU vision/text는 ARIES MXQ. CPU fallback으로 대체하지 않았다.

발표자 설명: “이 결과는 서로 다른 정밀도·호스트·runtime의 실제 실행 구성 비교입니다. 품질 점수는 제외했고, GPU 경로의 긴 TTFT 원인은 후속 프로파일링이 필요합니다. 배치 정책 또는 새 알고리즘의 우월성 결과는 아닙니다.”

## 슬라이드 2 — 캐시 존재와 실행 준비 완료는 다르다

그림: `readiness-cost.png` 또는 SVG.

- 최초 SD 준비: 8.85GB, 전체 검증·게시까지 **73.23분**.
- 다음 Pod는 **재전송 0회**였지만, 캐시 전체 검증 **6.92분** + 모델 process load **3.05분**이 필요했다.
- 준비 비용을 warm 추론 지연에 섞지 않고 별도 측정해야 한다.

발표자 설명: “이번 관측은 파일 캐시와 모델 로드 상태를 구분할 필요성을 보여줍니다. 다음 설계의 상태 신호 후보는 캐시 존재·무결성 검증 완료·장치 모델 로드·첫 추론 검증의 구분입니다. 이를 이용한 정책 이득이나 신규성은 아직 검증하지 않았고, 같은 상태 정보를 받은 기존 DAG 재최적화·hysteresis와 비교해야 합니다.”

각주: 별도 2회 실행의 관측이며 host/driver/OS cache를 독립 초기화하지 않았다. 그림은 GPU의 두 준비 단계 합계이고 coordinator upload·NPU 준비는 제외한다. 통제된 개선율 실험이 아니다.

## 부록 — SD I/O를 관측한 준비 과정

그림: `sd-preparation.png` 또는 SVG.

- 최대 4MiB/s, SD busy와 fsync 지연에 따라 자동 감속·정지.
- pause 17회, 총56.87초. 캐시 단계 snapshot 73개 모두 node Ready=True.
- 전체 파일 hash/모드 검증 후 원자적으로 게시. 같은 PVC를 다음 실행에서 재사용했다.

각주: 간헐 관측이며 연속 가용성을 보장하지 않는다. 모델 로딩 읽기 I/O는 다운로드 쓰기 제어 범위 밖이다.
