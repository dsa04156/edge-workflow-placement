# 품질·네트워크 인지형 이기종 엣지 AI 파이프라인 오케스트레이션

**Quality- and Network-Aware Orchestration of Multi-Stage AI Inference on Heterogeneous Edge Nodes**

갱신일: 2026-10-23. 사용자가 지정한 연구 방향이다. 실행 시스템의 설계·평가 기준이며, 새로운 구현이나 성능 우위가 검증되었다는 뜻은 아니다. [이전 문제 정의](problem-definition-20261016.md)와 기존 실험 자료는 보존한다. 현재 실험 기준은 [품질·네트워크 인지 실험 계획](quality-network-experiment-plan.md)이다.

## 1. 연구 목표

**AI 서비스가 요구하는 품질을 지키면서, 여러 엣지 장치의 서로 다른 연산 능력과 네트워크를 활용해 더 많은 요청을 제시간에 처리한다.**

같은 자원 예산·유입 요청·품질 요구조건에서 기한 내 완료하는 요청 수를 늘리는 실행 시스템을 연구한다. 이종 노드·품질·네트워크·DAG는 유지하며, 배치 알고리즘은 프로파일링·후보 검증·실행·관측을 연결하는 시스템의 한 구성 요소로 다룬다. 시스템 구현 자체나 여러 변수를 함께 고려한다는 사실만으로 신규성을 주장하지 않는다.

검증 질문은 다음과 같다.

1. 같은 배치 방법에서 품질 제약의 적용 유무가 최종 품질과 기한 내 완료 성능을 어떻게 바꾸는가?
2. 같은 품질 조건에서 통신비용을 반영하면 어떤 입력 크기·네트워크·부하에서 이익이 생기거나 사라지는가?
3. 가까운 기존 품질·네트워크 인지 방법과 같은 자원·정보·실행 기회를 제공했을 때에도 이익이 남는가?
4. 관측·선택·준비·전환 비용과 대기를 포함한 전체 구간에서도 이익이 유지되는가?

Task별 fastest-feasible와 DAG 공동 배치의 차이는 두 번째·세 번째 질문의 원인 분석으로 유지한다. 새 DRL/GNN이나 예측 모델의 필요성은 전제하지 않는다.

## 2. 서비스와 범위

워크로드 범주는 **다단계 AI 추론**, 대표 평가 서비스는 **멀티모달**이다. 시작 후보는 영상 전처리→영상 추론, 음성 전처리→음성 인식의 두 분기를 결합하여 최종 응답 또는 이벤트를 판단하는 DAG다. 멀티모달 자체를 기여로 삼지 않는다.

두 분기의 입력은 동일 서비스 요청에 속하고, 결합이 의미 있는 정답 라벨과 평가 규칙이 있어야 한다. 임의의 이미지와 음성을 붙이거나 두 모델의 출력을 단순 연결한 실행 성공만으로 서비스 품질을 검증하지 않는다. 현재 구현 후보는 이미지와 음성 질문을 결합하는 VQA(ResNet18·Wav2Vec2·MUTAN)이며, 기존 60쌍 자료의 서비스 품질 미달은 해결 과제로 남아 있다.

- 입력 source는 엣지로 고정한다. 센서 위치와 전처리/추론 위치를 구분하고 최초 입력 전송과 최종 응답 전달도 측정한다.
- CPU·GPU·NPU는 해당 모델·실행 설정의 실제 실행과 품질 검증을 통과한 경우만 후보로 사용한다. 특정 장비에서 다른 모델의 smoke 성공은 새 모델의 근거가 아니다.
- 보유 장비 전체를 검증 대상에 유지하며 CPU 전용으로 연구 범위를 축소하지 않는다. 현재 점유·노드 장애·도구 미확보·모델 미검증·실제 실패를 구분한다. 일부 조합의 실패를 가속기 계열 전체의 미지원으로 일반화하지 않는다.
- 첫 비교는 모델·가중치·정밀도·전처리·결합 규칙을 고정한다. 이후 지원되는 정밀도 또는 모델 변형을 별도 실험으로 추가한다.
- 대형 VLM 내부 레이어 분할, 새 에이전트 프레임워크, 미래 부하 예측 학습 모델은 필수 범위에서 제외한다. GPU 자원 분할은 사용한다면 기반 기능이며 별도 신규성으로 삼지 않는다.
- 기존 서버를 포함하면 노드별 역할과 자원 예산을 명시한다. 서버의 실행 성공을 엣지 가속기 검증으로 바꾸어 부르지 않는다.

## 3. 시스템의 입력과 결정

DAG의 Task를 `v`, 실행 설정을 `c=(노드, 가속기, 런타임, 모델/산출물 버전, 정밀도)`로 기록한다. 계획 `p`는 Task별 설정과 데이터 전달 경로를 정한다.

| 구성 | 필요한 근거와 역할 |
|---|---|
| 실행 후보 등록 | 연산자·dtype·shape·runtime/driver·메모리 적합성, 실제 실행 장치, 모델/파생 산출물 hash, fallback 여부 |
| 실측 프로파일 | Task 실행시간과 분산, 메모리, 준비 상태·시간, 동시성/간섭 조건, 관측 시각 |
| 품질 검증 | 정답이 있는 데이터셋에서 단계별 지표와 최종 서비스 지표, 데이터 분할·표본 수·허용 기준 |
| 데이터 경로 | 실제 입력/중간/출력 bytes와 표현, 직렬화·복사·전송시간, 공유 링크 경합 |
| 현재 상태 | 자원 가용량, 큐·실행 중 요청, 네트워크 관측값과 정보 나이, 모델 준비 상태 |
| 계획 선택·적용 | 품질·호환성·자원 제약을 만족하는 구성의 종단 성능을 비교하고 요청/Task 경계에서 실행 위치 적용 |
| 실행·계측 | 요청 ID·deadline·계획 버전·stage receipt·출력·실패·드롭과 모든 제어 비용 기록 |

첫 구현의 판단 근거는 사전 실측 프로파일과 현재 관측 상태로 제한한다. 개별 Task의 가장 빠른 노드뿐 아니라 DAG의 병렬 분기·합류 대기·계산·전송을 함께 고려한다. 정적 배치만으로 부하에 따른 대기를 설명할 수 없으므로 큐와 동시 실행 한도도 기록한다. 수락·드롭·batching·복제 정책은 첫 비교에서 고정하고, 이를 변경한다면 별도 실험 축으로 명시한다.

## 4. 품질 계약

품질은 장치의 고정 속성이 아니다. 특정 데이터 분포에서 모델·실행 설정·파이프라인을 평가한 결과다. 단계별 accuracy/mAP/WER 등은 진단용이며, 최종 품질은 전체 파이프라인의 출력으로 측정한다. 단계별 정확도를 곱해 최종 품질로 대체하지 않는다.

품질 평가의 단위는 사전에 정한 데이터셋 또는 요청 집단이다. 개별 요청의 정답을 보장하거나 온라인에서 정답을 미리 아는 것으로 취급하지 않는다. 프로파일/품질 보정 자료와 최종 평가 자료를 분리하고, 평가 정답을 배치 결정에 제공하지 않는다. 요청에 따라 설정을 섞는 정책은 개별 후보의 통과 여부뿐 아니라 실제 정책이 생성한 출력 집단의 품질도 평가한다.

모든 실행 설정이 같은 품질 기준을 통과하고 출력도 같다면, 품질 제약의 적용 유무에 따른 성능 차이는 없을 수 있다. 이를 품질 인지 효과의 증거로 만들지 않는다. 품질 차이가 관측되는 지원 설정을 추가할 경우 모델 선택 효과와 배치 효과를 분리한다. CPU reference와의 수치 일치는 정답 품질과 별개다.

## 5. 주 지표와 비용 경계

주 지표는 **서비스 품질 요구조건을 충족한 실험에서의 초당 기한 내 완료 요청 수(goodput)**다. 품질은 실험/요청 집단 수준의 제약으로 보고하며 각 기한 내 요청이 정답이라는 뜻으로 세지 않는다.

고정된 유입 구간 길이 `T` 동안 발생한 전체 요청 집합을 `A`라고 할 때:

`G = |{r ∈ A : 유효한 최종 응답 완료, 완료시각 ≤ 발생시각 + D_r}| / T`

`D_r`는 사전에 정한 요청별 deadline이다. 마지막 유입 뒤에도 해당 cohort의 deadline까지 추적하며, 이 지표는 유입 cohort 기준 rate로 명시한다. 짧은 burst 결과를 장기 정상상태 처리량으로 해석하지 않고, 정상상태 분석의 warm-up·측정·drain 경계는 별도 사전 고정한다. 유효 응답은 프로토콜/서비스 형식상 완료를 뜻하며 정답 여부와 다르다.

- 모든 조건에 `G`, 서비스 품질 값과 기준 충족 여부를 나란히 보고한다. 품질 미달 조건의 처리량을 동일 품질 개선으로 주장하지 않는다.
- 기한 내 완료율의 분모는 수락 요청이 아닌 전체 유입 요청이다. 거절·드롭·실패·시간 초과·최종 미완료를 빠뜨리지 않는다.
- 종단 p50/p95/p99, offered/admitted/completed rate, 큐 길이·대기시간, 실패·드롭률을 보조 지표로 기록한다. 성공 요청만의 지연 통계는 그 조건을 명시한다.
- 반환 출력 품질과 반환 coverage를 함께 보고한다. 쉬운 입력만 남겨 품질이 높아지는 선택 편향을 확인하기 위해 사전 요청 집단별 품질·완료율과 누락 수를 공개한다. 미반환 입력의 처리 규칙은 서비스별로 사전 고정한다.

종단 시간은 엣지에서 예정된 요청 발생부터 최종 응답 수신까지다. 실제 release가 늦으면 그 지연도 포함하고, 발생기 용량 부족은 시스템 거절과 별도 기록한다. 입력 수집/인코딩을 제외한 replay이면 경계를 표시한다. 준비·로딩·전송·복사·큐·재시도·관측·선택·전환 비용을 추적하되 병렬 분기·중첩 RPC 시간을 단순 합산하지 않는다. 정상 구간과 배포/전환 포함 구간을 구분한다.

## 6. 비교와 기여 판단

공통 실행기·요청 trace·자원 예산·기술적 실행 후보·프로파일·관측 기회를 맞춘다. 품질 제거 ablation만 품질 제약을 의도적으로 제거하고, 호환성·용량 제약은 유지한다. 통신 제거 ablation은 선택기의 통신비용 항목만 제거하며 실제 데이터 전송은 유지한다.

Task-fastest, 통신 인지 greedy, 기존 DAG 재최적화와 단순 hysteresis를 강한 단순 기준선으로 둔다. kube-scheduler/Koordinator는 운영 기준선이며 이것만 이긴 결과로 시스템 기여를 결론 내리지 않는다. 근접 선행 비교는 [문헌 대조](quality-network-orchestration-related-work.md)에 확인 수준을 기록한다. 기존 DRL 비교 계획은 유지하되 서비스·목적함수·실행 계약이 맞는 구현의 선정과 비용 보고가 먼저다. 모든 정책군의 전수 구현을 첫 파일럿 조건으로 두지 않는다.

신규성은 가까운 기존 방법과 같은 정보의 단순 보완 이후에도 남는 문제와, 그 문제를 해결하는 실행 메커니즘 및 재현 가능한 효과로 판단한다. 이득이 없는 고대역폭·저부하·연산 지배 조건도 보존한다.
