# 이종 엣지 AI 환경에서 실행 호환성과 데이터 이동 비용을 고려한 동적 워크플로우 배치 최적화

**Runtime- and Data-Aware Dynamic Workflow Placement for Heterogeneous Edge AI Systems**

갱신일: 2026-10-16. 사용자 지정 주제와 핵심 질문을 반영한 현재 문제 정의다. 이전의 모델 준비·실행·재배치 비용은 이 주제의 비용 항목으로 이어가며, 새 알고리즘의 필요성·신규성·성능 우위는 미확정이다. 첫 실험의 상세 조건은 [실험 계획](workflow-placement-experiment-plan.md)을 따른다.

## 1. 핵심 질문과 검증 순서

**개별 Task마다 가장 빠른 노드를 선택하는 것과, DAG 전체를 고려해 실행 위치를 결정하는 것 사이에 실제로 얼마나 차이가 나는가?**

여기서 가장 빠른 노드는 실행 호환성과 자원 제약을 만족하는 후보 중 Task 자체의 예측 실행시간이 가장 짧은 노드다. 데이터 전송·대기·준비를 함께 보는 단순 greedy도 별도 비교하여 약한 기준선에만 이기는 결과를 피한다.

| 질문 | 비교 | 판단할 것 |
|---|---|---|
| RQ1. DAG 공동 결정의 실익은 얼마인가? | Task별 fastest-feasible 대 DAG 전체 배치; 먼저 정적 환경 | 중간 데이터·의존성·병목을 함께 고려한 종단 지연과 완료율의 차이 및 차이가 없는 조건 |
| RQ2. 기존 정책이 동적 변화에 적응하는가? | 고정 DAG 계획 대 최신 정보로 재최적화하는 기존 DAG 정책; 운영·DRL 정책도 비교 | 변화 크기·지속시간·관측 지연에 따른 실행 실패, SLO 손실과 회복시간 |
| RQ3. 새로운 방법이 필요한가? | 기존 DAG 재최적화 대 프로파일 갱신·전송 인지 greedy·hysteresis 등 단순 보완 | 전체 비용을 포함해도 재현 가능한 손실이 남는지, 원인이 정책·관측·실행 계층 중 어디인지 |

RQ1에서 DAG 방식의 우위를 보이는 것만으로 신규성을 주장하지 않는다. 차이가 작거나 기존 방법의 갱신으로 충분하면 새 알고리즘 개발을 보류하고 연구 범위를 조정한다.

## 2. 선행연구와의 경계

- **JellyBean**은 이종 인프라에서 ML 워크플로의 모델 선택·worker 배정을 함께 다룬다. DAG 공동 배치와 계산·네트워크 비용을 처음 결합한다는 주장은 성립하지 않는다. [저자 논문 정보](https://arxiv.org/abs/2205.04713)
- **AnchorDL**은 데이터 전송과 memory-resident model weights에 따른 로딩 비용을 함께 고려하고 인접 의존성을 보는 look-ahead를 사용한다. 공식 초록은 chain·fan-in·fan-out 및 greedy joint-cost와의 비교를 명시한다. 따라서 데이터·모델 위치/준비 비용 결합이나 greedy 개선 자체는 새 기여가 아니다. [공식 초록](https://pure.korea.ac.kr/en/publications/anchordl-dual-locality-based-scheduling-for-serverless-inference-/), [확인 수준·남은 원문 검토](ieee-11662529-review.md). NPU/runtime 호환성·컴파일·전환 범위는 아직 미확인이다.
- **Atlas**는 모델 선택과 하드웨어 배치를 공동 결정한다. 검토본 §III-A는 단일 사이트의 offline 계획과 무시할 수 있는 단계 간 통신 비용을 가정한다. 변화하는 엣지 링크에 적용하는 것은 이 가정의 확장이며 원 논문의 결함으로 단정하지 않는다. 이 문서의 Atlas는 `arXiv:2609.04513v1`을 뜻한다. [원문 §III-A·V](https://arxiv.org/html/2609.04513v1)
- Kubernetes DRL에서 GPU/NPU를 고려한 직접 선행도 있다. [별도 조사](kubernetes-drl-heterogeneous-accelerators.md)의 근거를 유지한다.

조사 범위 안에 없는 기능을 선행연구 전체의 미해결 공백으로 일반화하지 않는다. 논문·코드·버전별 정적/동적 계획과 실제 재배포 기능은 구현 선정 시 추가 대조한다.

## 3. 대상과 범위

첫 검증은 Kubernetes 환경에서 **3~5개 Task의 실제 AI 추론 워크플로**를 대상으로 한다. Task는 모델 추론뿐 아니라 전처리·후처리 같은 실행 단계를 포함한다. 합성 sleep 태스크만으로 실제 AI 워크플로를 대체하지 않는다.

- 서로 다른 성능과 실행환경을 가진 실제 노드에서 동일 입력을 처리한다. CPU·GPU·NPU 구성 중 보유 장비와 검증된 런타임에 맞춰 선택한다. NPU 확보나 특정 벤더 채택을 가정하지 않는다.
- 1차로 모델·정밀도·입력 조건을 고정하여 배치 효과를 분리한다. 실행환경 간 출력 오차와 최종 품질 허용 기준을 확인한다.
- 네트워크 대역폭·지연 변화, 런타임 가용성 변화, 모델의 warm/cold 상태 변화를 한 축씩 검증한 뒤 필요한 조합만 추가한다.
- 초기 동적 실험은 Task/요청 경계에서 새 배치를 적용한다. 진행 중 GPU/NPU 커널이나 메모리 상태의 임의 live migration은 전제하지 않는다.
- 모델 버전 갱신·학습·KV/optimizer 상태 이전·자동 모델 분할은 첫 실험의 필수 범위가 아니다. 필요성이 확인될 때 별도 범위를 정의한다.

## 4. 배치의 입력·행동·제약

워크플로는 DAG `G=(V,E)`이며, 노드 `v`는 Task, 간선 `(u,v)`는 데이터 의존성이다. 실행 노드는 `n`, 시점은 `t`로 표시한다.

| 정보 | 작업용 정의 |
|---|---|
| 실행 호환성 `F(v,n,t)` | 모델 버전·연산자·dtype·shape·runtime/driver·메모리·품질 요구를 실제로 만족하는지. 미확인은 실행 가능으로 간주하지 않음 |
| 준비 상태 `R(v,n,t)` | image·모델 산출물·컴파일 결과·상주 여부와 추가 준비시간. cold라고 반드시 실행 불가인 것은 아님 |
| 계산·대기 | Task별 실측 실행시간, 현재 큐·자원·간섭과 관측 시각 |
| 데이터 경로 | 간선별 중간 데이터의 실제 위치·크기·형식, 직렬화·복사·전송시간, 유효 대역폭·지연·공유 링크 경합 |
| 현재 배치 | 실행 중 Task·완료 산출물·재배치 가능한 경계 및 적용 중인 계획 버전 |

행동은 실행 가능한 Task–노드 배치와, 이후 요청에 대한 배치 유지/갱신이다. 준비·자원 확보가 끝나지 않았으면 대기할 수 있다. DAG 선행 조건, 자원 용량, 데이터 도착, 품질과 SLO를 지킨다.

데이터 경로의 지연은 단순한 `bytes / bandwidth` 추정으로 시작할 수 있으나 실제 직렬화·전송·대기시간으로 검증한다. 같은 노드에서도 CPU–가속기 복사나 IPC 비용이 있으므로 무조건 0으로 두지 않는다. fan-out 데이터는 실제 전송 횟수대로 측정한다.

## 5. 목적과 비용 경계

1차 주 지표의 제안은 **요청별 DAG 종단 지연의 p95**다. 동일 입력률·품질·자원에서 SLO 내 완료율, 실패·미완료율, 처리량을 함께 보고한다. 실패 요청을 지연 통계에서 제거해 빠르게 보이는 결과를 피한다. 과부하 여부와 관측 구간도 고정한다.

| 항목 | 측정 경계 |
|---|---|
| 종단 지연 | 입력 수신부터 마지막 Task의 유효 결과까지. 큐 대기·준비·전송·재시도 포함 |
| 중간 데이터 이동 | Task 사이의 payload·직렬화·host/device 복사·네트워크 전송·대기 |
| 모델 준비 | 필요한 image/artifact 전송·변환/컴파일·로딩·워밍업·검증 |
| 배치 전환 | 새 배치 준비·라우팅 변경·drain·중단·재실행과 복구. 이전 계획의 미완료 요청도 추적 |
| 제어 비용 | 모니터링·프로파일 수집·최적화·DRL 학습/추론의 시간과 자원 사용 |

동시에 수행된 준비·계산·전송은 실행 타임라인으로 분석하며 단순 합으로 종단 지연을 만들지 않는다. 준비와 전환에 같은 작업을 중복 계상하지 않는다. 시간·비용·에너지를 임의 가중합으로 섞지 않는다.

## 6. 실패 가설과 반증 기준

다음은 관측 결과가 아닌 검증 가설이다.

- Task 계산시간 절약보다 경계 간 데이터 이동 증가가 커져, 개별 최단 실행 노드 선택이 DAG 전체 지연을 악화시킬 수 있다. 저통신·동일 노드 최적 조건에서 차이가 사라지는지도 확인한다.
- 오래된 링크·실행환경 정보로 실행 불가 또는 느린 계획을 선택할 수 있다. 같은 최신 정보를 주었을 때 손실이 사라지면 정책보다 관측/갱신 문제로 판단한다.
- 환경 변화의 지속시간이 전환비용 회수시간보다 짧으면 반복 재배치가 손실을 만들 수 있다. 기존 재최적화에 hysteresis를 추가해 해소되는지 확인한다.

새 방법은 가까운 기존 정책의 기능과 같은 정보·실행 기회를 제공한 비교에서도 남는 문제를 설명해야 한다. 실패하지 않는 조건과 단순 정책이 이기는 조건도 보고한다.

## 7. 다음 결정

실제 DAG·모델/데이터·장비 목록 → 호환성/데이터 경로 실측 → 정적 배치 비교 → 네트워크/실행환경 변화 재생 → 기존 재최적화·운영·DRL 정책 비교 → 새 방법 필요성 판단 순서로 진행한다. 구체 버전·반복 수·SLO·실질적 개선 기준은 파일럿 후 본 실험 전에 고정한다. [CPU/KubeEdge 기반](../experiments/e0-kubeedge.md), [전달·EdgeCore 관측](../experiments/e0-transport.md), [서버 GPU·NPU 준비/실행](../experiments/e0-accelerators.md), [576요청 프로파일](../experiments/e0-rpc-profile.md)을 확인했다.

[세 Task·64배치 파일럿](../experiments/e1-dag.md)에서 Task별 최단 실행은 전 GPU, 데이터 인지 greedy와 같은 표의 DAG 열거는 전 ARM을 골랐다. 새 평가 중앙값은 각각 73.584/69.818ms였지만 ARM의 긴 관측값이 있어 tail/SLO 우위를 뜻하지 않는다. C1과 열거가 같은 배치를 골랐으므로 DAG 공동 결정의 추가 이득이나 새 알고리즘 필요성은 확인하지 못했다. Edge eth0의 측정 뒤 협상값100Mbps는 환경 관측이며 packet 경로/원인 확정은 아니다. 모델 변환·SDK download 준비 문제도 배치 알고리즘 실패와 구분한다.

[입력 위치·NPU 준비 상태 부분 실험](../experiments/e2-dynamic.md)은 ARM CPU/Intel NPU에서 source 변경과 실제 서비스 객체 eviction을 재생했다. 1,380개 평가 요청의 eviction 조건 평균은 초기 고정 배치107.08ms, 준비 비용 포함 DAG 재계산48.16ms였다. 같은 정보의 greedy와 hysteresis도 모두 같은 배치 궤적이었다. 준비 보정 중앙값27.01ms는 server source에서 예상되는 1회 절감79.95ms보다 작아 짧은 변화에서도 준비 비용 회수가 예상됐다. 이번 조건은 준비 비용 누락의 손실이나 새 알고리즘 필요성을 입증하지 못했다.

[8입력·3새 배포 후속](../experiments/e3-input-replication.md)은1,344 workflow/측정960회를 확인했다. 엣지 warm 입력의 camera/chelsea/retina/rocket에는 세 배포 모두 더 빠른 NPU anchor가 있었고 astronaut 등은 ARM이 빨랐다. camera의 NPU Top-5는 CPU와1class가 달라 같은 품질의 이득으로 간주하지 않는다. 이는 dog 기반 비용표의 전이 경계이며, 최신 입력/품질 정보를 제공한 AnchorDL 등 기존 방법의 실패가 아니다.

후속 [AnchorDL 비교 준비 점검](anchordl-reproduction-contract.md)은 기존 실행기의 readiness/가중치 상주·요청 상각/DAG look-ahead 의미 차이를 확인했다. [공식 metadata](anchordl-source-acquisition.md)로 DOI와 IEEE11662529의 연결은 확인했으나 원문·공식 코드는 미확보다. 다음은 비용식·look-ahead/cache·baseline 계약 확보와 같은 정보 비교, 여러 추론 단계와 분기/합류 DAG의 검증이다. 새 Pod3배포도 같은 host·날짜·driver/OS cache를 공유했다. 입력 위치 변화는 물리 링크 변화가 아니며 객체 재준비는 완전 cold가 아니다. 엣지 가속기·정답 품질 데이터셋·링크/호환성 변경·관측 지연·큐/경합·p95/SLO·네 필수 정책군 본 비교는 아직 검증하지 않았다.

원문과 독립적인 [공통 정책 연결](../experiments/common-policy-runner.md)은 구현했다. 로컬 CPU worker2개에서 snapshot·후보/입력 profile·준비 상태 변경·실제 HTTP receipt를 검증했으며 전체17개 회귀를 통과했다. synthetic 비용표를 사용한 연결 검증이므로 실제 정책 간 성능 차이나 새로운 실패 조건의 근거는 추가하지 않는다.

[E2 실측 표 연결](../experiments/measured-policy-bridge.md)은 여섯 정책에 같은 snapshot을 제공한60개 결정과 대표10+준비2회 실제 ARM/NPU 실행을 확인했다. 과거 표에서 네 적응 정책의 선택은 같았으며 Task-fastest의 server 입력은 후처리만 ARM에 두는 혼합 배치였다. 이는 결정·적용 호환성 검증이다.

이후 [최신 보정·품질 후보 동결 평가](../experiments/fresh-placement.md)는8입력·3새 배포의 보정1,536회와 별도 평가679회/측정485회를 완료했다. camera는 입력을 유지하고 사전 품질 규칙으로 NPU 추론만 제한했다. 균등 집계 평균 total은 Task-fastest51.64ms, greedy43.56ms, 작은 DAG 열거38.59ms였다. greedy와 DAG는48조건 중35개에서 같은 계획이었고, 다른13개 중11개에서 DAG의 관측 평균이 낮고2개에서 높았다. 이는 warm 정적3Task chain의 기술 통계이며 독립 환경/미관측 입력 일반화·AnchorDL 실패·새 알고리즘 필요성의 근거로 확대하지 않는다.

당장의 검증 과제는 hubble의 작은 보정 예측 이득이 평가에서 역전된 원인과 chelsea에서 workflow 이득이 observation/state_validation 때문에 total 이득으로 이어지지 않은 비용 경계다. 같은 정보를 가진 기존 방식의 갱신과 단순 비용 반영부터 확인한 뒤 실제 변화·여러 추론 단계·분기/합류로 확장한다. 첫 보정 시도의 중첩 HTTP idle 오류는 [실행 계층 문제로 재현·수정](../experiments/transport-idle-diagnosis.md)했고 부분 데이터는 새 비교에 합치지 않았다.
